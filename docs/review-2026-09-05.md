## Confirmed defects and changes

### Expanded blank slot

Build 1307 left an enabled narrow Ice-owned status item in the native bar.
Although its requested width was one point and AX reported a width of three,
the native layout reserved an approximately 17-point slot. It was a real
Ice-owned empty item, not a Layout placeholder or another application's icon.

`MacOS27NativeMenuBarHiding` now withdraws this item while expanded and while
Layout is idle. It publishes a narrow drag handle only for explicit hiding or
reordering, then either widens it for hiding or withdraws it again. It preserves
only Ice's own saved position. No other application's preferences are changed.

An intermediate build 1308 exposed a second, reproducible defect: reinserting
the handle and immediately trusting owner AX frames could select Spotlight
instead. The native Volume-to-visible drag was initially correct, but the next
hide unexpectedly moved Spotlight to the hidden side. That build was replaced.

The common boundary alignment path now waits 200 ms for the insertion layout
transaction, reads fresh frames, and refuses to drag unless the source AX hit
test identifies the exact Ice-owned boundary. Source and destination must be
valid menu-bar rectangles on the same display. Adjacency and side are verified
again before hiding. There is no retained-frame fallback in that verification.
A newer expand request cancels the pending hide; failed verification leaves the
bar expanded. The reproduced sequence passed on 1309 and 1310 afterward.

The brief settling interval is deliberate correctness protection, not a custom
animation. It was not removed merely to reduce an apparent timing number.

### Layout glyphs and stale work

- A WeChat AX extra at `(-1, 1105, 40, 24)` was not a real menu-bar item but
  appeared as a blank Layout tile. Enumeration now requires a positive-sized
  frame whose center is within a real display's menu-bar strip.
- Entering Layout performs one full owner refresh to discover newly revealed
  or newly created native items. Subsequent editing refreshes use known owners.
- Layout startup is a cancellable SwiftUI task. Canceled enumeration cannot
  publish its result after an await. Merely opening Layout does not drag the
  boundary.
- Captures are single-flight, pending section requests are coalesced, and
  completions are rejected after editor/reorder generation changes. Capturing
  during native reordering is skipped.
- Unchanged image values do not re-run every glyph's foreground extraction or
  repaint every tile. Real captured glyphs remain transparent, labelled and
  uniformly spaced; no generic application-icon substitution was introduced.

### Native reorder and simpler updates

- Hiding and explicit Layout reorder use the same boundary alignment function.
  The latter does not overwrite the immediate requested-order preview.
- Synthetic drag error cleanup releases an in-progress mouse press.
- Equal persisted layout values, permission results and control appearance
  values are ignored rather than repeatedly written or published.
- The screen-capture permission-result cache is protected by a lock. No new
  permission-request path was introduced.
- The macOS 27 control no longer clears its image between state images.
- Sidebar selection was publishing during an AppKit-backed List update,
  producing SwiftUI render re-entry warnings. The equal-value guard alone on
  1310 was insufficient. Build 1311 publishes the change on the next main
  run-loop pass; the final repeated navigation test had no SwiftUI warning for
  the installed process.

### Optional appearance work

Appearance panels are reconciled when effects are disabled and on screen
changes. Existing panels observing the same configuration are not needlessly
recreated. Missing-frame retries were reduced from one-millisecond polling to
50 ms, and rejected updates now yield for 100 ms instead of immediately
repeating. These branches were statically reviewed and built, not exhaustively
device-tested in every appearance/fullscreen configuration. Existing bounded
tasks may finish after panel closure; immediate elimination of all background
work was not measured.

## Performance observations and limits

Short 1310 idle samples showed approximately 0.1–0.4% CPU and 62 MiB footprint.
The final 1311 eight-second sample spanning entry into Layout reported 58.0 MiB
physical footprint, 66.2 MiB peak, with 5,641 of 5,871 main-thread stack samples
in the event loop's Mach wait. These are limited local observations, not a
controlled before/after benchmark or a long-duration memory/energy test.

The concrete improvements are bounded/coalesced work, fewer equal-state
publications and elimination of a tight retry path. No general speedup
percentage or frame-perfect absence of jitter is claimed.

## Later checkpoint: native-drag lifecycle protection in 1326

This subsection describes later work and does not replace the historical 1311
acceptance record above. A read-only bundle/process check confirmed
`0.12.0-macos27.127 (1326)` installed at `/Applications/Ice.app`, running as PID
67180 with a 15:34:23 launch time. MenuBarAgent was still PID 59001, launched at
11:57:23. These observations identify the installed candidate, not a stress-test
result; real drag/cancellation stress on 1326 is still pending.

A separate, statically demonstrable race existed in the newer boundary-withdrawal
implementation: a newer expand request cancelled pending concealment and
immediately withdrew Ice's native boundary, while an already-started synthetic
boundary drag deliberately continued until mouse-up/Command-up. Cancellation of
the Swift task did not stop that event sequence. It was therefore possible to
withdraw or resize a scene while native drag events still depended on it.

The fix pins Ice-owned visibility changes for each native event sequence only.
This covers a source or target that is Ice-owned and third-party endpoints whose
positions would otherwise shift when Ice's boundary changed. While pinned,
`syncNativeVisibility()` records one pending resync, not a captured old intent.
After mouse-up, Command-up and cursor cleanup, `defer` releases the pin and reads
the current section/Layout state. No global input monitor is used. Asynchronous
AX result verification is outside the pinned interval, and the existing
cancellation/generation check prevents an old concealment completion from
overwriting a newer request. Cancellation before mouse-down releases the pressed
Command key without starting the drag; once mouse-down is posted, the sequence
still guarantees its releases.

`Tests/NativeDragVisibilityStateTests.swift` passes 20 pure state-sequence
assertions, including coalesced hide/expand, Layout entry/closure, cancellation
cleanup, retries and applying only the newest intent. The original 24 boundary
assertions also pass, as do scoped strict SwiftLint and `git diff --check`.
These tests do not execute native input or establish MenuBarAgent stability.

**This race is not the proven cause of the four earlier crashes.** Those crashes
occurred during the historical 1307 test interval, whose expanded policy retained
a narrow boundary rather than using the later withdrawal lifecycle. The four
system crashes remain open pending a controlled reproducer and verified remedy.

## Separating unrelated diagnostic warnings

AppKit logged negative view geometry during computer-use window sharing. Its
symbolicated stack ran through `_positionSharingIndicator`,
`NSWindowSharingSessionRecipientIndicator` and
`_windowSelectiveSharingStateChangedNotification`. This identifies the system
window-sharing indicator, not a Layout thumbnail frame. It was kept separate
from the actionable SwiftUI sidebar publishing warning fixed in 1311; no
speculative patch to AppKit internals was added.
